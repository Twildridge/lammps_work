# Building Input Data Files

[← back to README](../README.md)

A gel simulation starts from a `.data` file: a text file with every atom's position and type and the bond topology. The files are built on the Mac with the Jupyter notebooks in `scripts/` (a notebook is a Python document run one cell at a time; `jupyter lab` in a terminal opens them) or with the converter scripts in `scripts/lib/`. They are kept in `lammps_data_files_local/` next to the repo, catalogued in its `README.md`, and copied to `~/Documents/lammps_data/input_data/` on the cluster.

### Which notebook or script to use

The notebooks live in `scripts/`; the Python modules they import (converters, plate builder, CLI tools) live in `scripts/lib/` (since 2026-10-01), which the notebooks add to `sys.path` themselves.

The junctions are relaxed between switch sweeps (harmonic strand energy about the lattice strand length r₀, a soft repulsion between non-bonded junctions, the face junctions held in all three directions on anchors jittered by 0.25 r₀ so the lattice spacing is not re-formed, a weak tether of every junction to its lattice site that spreads the stretch; Metropolis acceptance annealed from T = 4 to 0.01 in units of the strand energy after six randomising sweeps; no switch may re-create a lattice pair and the lattice strands that survive the randomising sweeps are switched away; a final pass re-wires every strand longer than 1.9 r₀ and frees the tethers of junctions on any that resist; the hard ceiling is 2.45 r₀ = 5.6 σ end-to-end, beads 1.4 σ apart against the FENE R₀ of 1.5, after the harmonic push-off). The first version held the face junctions along the face normal only, at a quarter of the stiffness: the junctions the switching connects to partners deep inside were pulled up to 3 σ into the block and slid sideways, which showed as dents and loose loops on the surface (the outermost junction of a 4 × 4 σ face patch sat 1.3 σ inside the face on average, 17 % of patches recessed by more than 2 σ); the current settings give 0.46 σ and 3.6 % (the lattice: 0.05 σ and 0 %), reported by the check's `surface` line. `verify_network_isotropy(<file>)` reads a written file back and reports, for all strands, for the interior (more than 7 σ, three strand lengths, inside the faces) and for the skin, the strand fabric tensor, the fourth-rank anisotropy of ⟨n n n n⟩ (the Born term of the elastic tensor), the Steinhardt Q₄ / Q₆ of the strand directions and the Born-affine Zener ratio A_xz = C₄₄ / ((C₁₁ − C₁₂)/2) in the box frame, each against the same statistic for as many random directions; the verdict is the interior's: the tethered, pre-stretched faces imprint an in-plane bias that reaches two to three strand lengths in (⟨n_x²⟩ 0.27–0.31 within 4 σ of the x-faces, ⟨n_y²⟩ 0.27–0.30 at 2–8 σ from the y-faces, isotropic beyond 8 σ; it is not lattice memory, banning lattice pairs left it unchanged), the equilibration relaxes it with the pre-stretch, and the shear deck's grips and core margins sit on it. The second-rank fabric is 1/3 for every cubic lattice, so only the fourth-rank numbers can tell. The random preset builds `slab_support_5beads_tall_rho04_nowalls_random.data` from the rot45 geometry (`bond_switch = 3`, seed 7; 4.1 switches per strand accepted, no lattice pair left, strands 1.28 r₀ = 2.9 σ on average, one of 28 854 at 1.98 r₀ = 4.5 σ) and prints the check for it and for the two lattices: the random network's interior passes every metric (fourth-rank anisotropy 0.017 against 0.016 ± 0.004 random and 0.54 for the lattices; Q₄ 0.009 against 0.009 ± 0.002 and 0.51; A_xz 0.985 against 1.00 ± 0.01 random, ∞ aligned and 0 rot45), all strands together fail Q₄ through the skin (0.013), and the two lattices fail everything, as they must. ### Running the isolated-gel converter from the Terminal (2026-10-14)

`lib/add_more_plates_to_gel.py` has no notebook: run the script. If you only ever use JupyterLab, the easiest
terminal is the one inside it (**File → New → Terminal**); it already has the Python that runs your notebooks.

```bash
cd "<your lammps_work folder>/scripts/lib"            # quote the path, it has spaces
python add_more_plates_to_gel.py --layout x_plates \
    --input ../../../lammps_data_files_local/final_config_slab_support_5beads_tall_rho04_nowalls_1.0_1.0_8000000.data
```

`--layout six_plates` builds the `compress_slab` file, `--help` lists every option (bath margins, reservoirs,
plate park gap and overhang, `--no-log`, `--no-png`). `python` must be the Anaconda Python that runs JupyterLab
(`which python` shows which is active; `conda activate base` switches to it; on Dylan's Mac it is
`/opt/anaconda3/bin/python`). The same line works in a notebook cell with a leading `!`, with the path relative to
the notebook (`!python lib/add_more_plates_to_gel.py ...`). The script prints the geometry, the validation
(`RESULT: OK`, or the problems and nothing is written), the gel-unchanged check, the `slab_data_file_info.md` entry
it appended, and last `DATANAME for the batch file: <stem>`. Next to the input it writes `<stem>.data`, the
no sidecar since 2026-10-28; `--png` draws `<stem>_profiles.png` (density profiles along z and x: check that the gel sits
between the plates and pistons). Copy the `.data` file to `~/Documents/lammps_data/input_data/` on the cluster and
put the stem in the deck's batch (`shear_slab_two_pist_single.batch` for `x_plates`, `compress_slab_single.batch` for
`six_plates`). The periodic-slab converters (`slab_two_pistons_periodic.py`, `slab_shear_plates_periodic.py`) run
the same way; `slab_two_pistons_periodic.ipynb` is kept as their notebook front-end.

### The two-piston converter (2026-09-16)

`slab_two_pistons_periodic.ipynb` is not a lattice generator: it **starts from the equilibrated**
`final_config_slab_support_periodic_…_14000002.data` (the 2026-09-07 piston-transparent rerun) and only
re-arranges the box.  The reason is physical: the two-piston decks hold each reservoir at its pressure with
the NPT-piston scheme of Marioni et al. (J. Membr. Sci. 738 (2026) 124837, Eq. 3), which acts in *z only* —
`lx`, `ly` are fixed for the whole run — so it could never swell a fresh `pre_swell = 0.93` lattice laterally.
Starting from the aniso-NPH slab (σ_p,xx/σ_p,zz = 1.0005) the gel arrives with zero transverse network stress
and its equilibrium `lx`, `ly` and thickness *by construction*; the NPT-piston phase in the decks is then a
z-settle of the reservoirs, not a swelling equilibration.  Gel and solvent coordinates are copied verbatim
(one uniform z shift; the converter checks this).  Output: `<input stem>_two_pist.data` next to the input,
an entry appended to `slab_data_file_info.md` (no `.info.json` sidecar or png since 2026-10-28; `--png` draws the z-density histogram).  Knobs (Config cell / CLI): `permeate_thickness` (10 σ), `feed_thickness` (None =
keep), `margin_perm` (feed + 5 σ), `margin_feed` (15 σ — the feed piston rises by ~strain·L₀ under
compression, so raise it for sweeps beyond ε ≈ 0.10; the converter prints the limit), `piston_clearance`,
`load_piston_frac`, `sheet_source` (`support` copies the input sheet's pattern, 23,316 beads; `hex` rebuilds
at `sheet_spacing`).  If the 14000002 file is not on your Mac the notebook falls back to the 14000000 snapshot
as a **smoke-test input only** and says so.

`shear_slab_two_pist` — one deck since 2026-10-28 (the periodic one is archived). The **isolated-gel deck** (`shear_slab_two_pist.lmp`) reads the **`x_plates` layout** of `lib/add_more_plates_to_gel.py` (on the `slab_with_support_single.batch` final config → `<stem>_x_plates.data`: gel, bath, wet pistons and the two grip plates parked outside the x-faces, which the deck seats and drives); the same notebook with `layout = "six_plates"` builds the `compress_slab` file, and that file runs in the shear deck too (it deletes the four plates it does not use). The archived **periodic deck** (`archive/simulations/shear_slab_two_pist/shear_slab_two_pist_periodic.lmp`, 2026-10-03) needed **no data file of its own**: it reads the `<stem>_two_pist.data` file of `slab_two_pistons_periodic.ipynb` unchanged (the support and the load piston stay parked, the shear is applied through the polymer face layers), so anything built for `triaxial_compression_two_pist` can be sheared as is.

Shear-modulus pipeline **from the periodic slab (the archived `shear_slab` deck, 2026-09-22)**: `python scripts/lib/slab_shear_plates_periodic.py` (defaults point at the 14000002 slab in `lammps_data_files_local/`; knobs `--clearance 0.5 --spacing 1.5 --offset 0.5 --cutoff 2.5 --box-buffer 2.0`) → copy the `*_with_plates.data` it writes to `~/Documents/lammps_data/input_data/` on the cluster → `sbatch shear_slab.batch` (its `DATANAME` already names this file). The plates sit on the slab's z-faces (z = gap, x = shear, the same axes as the compression decks), so the shear gap is the slab thickness (plate separation ~120 σ) and the sheared membrane is laterally periodic (48 × 48 σ). The older isolated-cube pipeline (`isolate_gel.ipynb` → `add_plates_to_gel_periodic.ipynb`, plates on the x-faces of a finite gel driven ±z, 2026-04-28) needs the pre-2026-09-22 revision of `shear_slab.lmp` and the pre-2026-09-23 `shear_analysis.ipynb` (git history).

### Workflow for a new gel

1. Open `data_file_generator.ipynb` (isolated gel; pick `NETWORK`) or `slab_with_support_periodic.ipynb` (x/y-periodic slab).
2. Set the unit-cell count, beads per chain, pre-swell and solvent density.
3. Run all cells. The `.data` file lands in `../../lammps_data_files_local/`; its name encodes the parameters.
4. Copy it to `~/Documents/lammps_data/input_data/` on the cluster and run the equilibration batch.
5. Convert the equilibrated final configuration with the converter the production deck needs (table above).

Every generated file gets an entry in [`slab_data_file_info.md`](../slab_data_file_info.md), and the folder is catalogued in `lammps_data_files_local/README.md` (2026-10-11): one row per file with the measured solvent density, provenance, the batch that used it and its status. Active files stay at the top level; obsolete lineages are in `archive/<date>_<lineage>/`. The `rho` in a raw file's name is the generator's nominal density and was wrong for some files (`rho6` = 1.0; the cubes `new_02` = 0.6, `new_03` = 1.0): the two current ones were renamed to `rho10` (= 1.0) on 2026-10-11.
